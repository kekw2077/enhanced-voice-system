# Шина событий Nexus Anima — спецификация

Версия 0.4 · черновик для реализации в Python-сайдкаре

## Принципы

1. **Шина одна.** Все источники пишут в одну очередь. Никаких прямых вызовов «датчик → голос» в обход неё, иначе через месяц никто не поймёт, почему ассистент заговорил.
2. **Событие — факт, а не команда.** Источник сообщает «пинг вырос до 8% потерь», а не «скажи про пинг». Что делать — решает фильтр.
3. **Модель — дорогой ресурс.** Всё, что можно решить правилом, решается правилом. LLM будится, только когда нужна формулировка или неочевидный выбор.
4. **Молчание — валидный исход.** Большинство событий должны умирать в фильтре. Ассистент, который комментирует всё, выключается в первый же вечер.

## Формат события

```json
{
  "id": "01J8X...",
  "ts": "2026-08-31T14:02:11.482+03:00",
  "source": "net.relay",
  "type": "net.loss.high",
  "severity": "alert",
  "subject": { "route": "vps-fra", "app": "ChaosZeroNightmare.exe" },
  "payload": { "loss_pct": 8.4, "rtt_ms": 71, "window_s": 10 },
  "context": { "session": "gaming", "foreground": "ChaosZeroNightmare.exe", "user_present": true },
  "dedup_key": "net.loss.high:vps-fra",
  "cooldown_s": 300,
  "ttl_s": 60
}
```

| Поле | Зачем |
|---|---|
| `type` | Иерархия через точку, по ней матчатся правила: `net.*`, `net.loss.*` |
| `severity` | `info` — только в журнал; `notice` — можно озвучить; `alert` — пробивает тишину |
| `subject` | К чему относится событие. Ключ дедупликации строится отсюда |
| `context.session` | `idle` / `work` / `gaming` / `afk` / `dnd`. Главный переключатель поведения |
| `dedup_key` | Одинаковый ключ в окне `cooldown_s` — событие поглощается, счётчик повторов растёт |
| `ttl_s` | Протухшее событие выбрасывается из очереди не обрабатываясь. Новость про пинг через минуту никому не нужна |

Обязательный минимум: `id`, `ts`, `source`, `type`, `severity`. Остальное по возможности.

## Источники

| Источник | Тип событий | Как снимать | Частота |
|---|---|---|---|
| `voice` | `voice.command`, `voice.wake` | GigaAM + VAD | по факту |
| `system.process` | `process.started`, `process.stopped` | WMI-подписка или опрос psutil | 2 с |
| `system.window` | `window.foreground` | `SetWinEventHook` | по факту |
| `system.metrics` | `metrics.cpu.high`, `metrics.gpu.hot`, `metrics.vram.low` | опрос, наружу только пересечение порога | 5 с |
| `net.relay` | `net.loss.high`, `net.loss.recovered`, `net.rtt.spike` | пробы Nexus Relay | проба 1 с, агрегат 10 с |
| `job` | `job.done`, `job.failed` | Lumina, Sonara, длинные задачи | по факту |
| `overlay.czn` | `overlay.attached`, `overlay.ocr.failed` | оверлей-переводчик | по факту |
| `notify` | `notify.incoming` | Windows-уведомления, ntfy | по факту |
| `agent.nexus` | `agent.command`, `agent.pc.request` | мобильное приложение | по факту |
| `power` | `session.idle`, `session.resumed`, `session.locked` | Win32 idle timer | 30 с |
| `schedule` | `timer.fired` | внутренний планировщик | по факту |
| `screen` | `screen.frame` | скриншот **только по запросу правила или голоса** | никогда постоянно |
| `arbiter` | `model.evicted`, `model.ready`, `model.idle` | арбитр загрузки моделей | по факту |
| `nextcloud` | `nc.log.error` | хвост `nextcloud.log` по SSH | 5 с |

Правило про `screen`: кадр не публикуется в шину сам по себе. Его запрашивает обработчик, когда уже решил, что без картинки не обойтись. Иначе GPU уйдёт на разглядывание обоев.

## Фильтр: четыре шага

Событие проходит их по порядку и на любом может умереть.

### Шаг 0 — нормализация и дедуп

- Проверка `ttl_s`, отбрасывание протухших.
- Поглощение по `dedup_key` внутри `cooldown_s`: остаётся первое событие, у него растёт `repeat_count`.
- Гистерезис для порогов: `net.loss.high` взводится на 5% и снимается только ниже 2%, иначе на границе будет дребезг.

### Шаг 1 — детерминированные правила

Правила из `rules.yaml`, первое совпавшее выигрывает — если только у правила не стоит `continue: true`, тогда проверка идёт дальше по списку. Это нужно, когда одно событие запускает несколько независимых реакций (запуск игры одновременно переключает звук и поднимает оверлей).

Четыре исхода:

- **DROP** — только в журнал.
- **ACT** — выполнить инструмент из белого списка молча, без модели. Опционально короткий фиксированный отчёт голосом.
- **ASK** — задать вопрос и подождать ответа. Механика в разделе «Отложенные вопросы».
- **RAISE** — передать модели, потому что нужна формулировка, выбор или разговор.

Выбор между ACT и ASK решается одним признаком: **обратимое делай молча, необратимое спрашивай.** Переключить вывод звука, приглушить, поднять оверлей — обратимо, вопрос только раздражает. Закрыть приложение, отправить сообщение, удалить файл — спрашивай всегда.

### Шаг 2 — бюджеты и режимы

Проверяется до пробуждения модели.

- **Квота реплик.** Token bucket: `gaming` — 3 в час, `work` — 6 в час, `idle` — без лимита. `severity: alert` квоту игнорирует.
- **Тишина.** Полноэкранное приложение, активный микрофон в звонке, режим `dnd`, ночные часы — проходят только `alert`.
- **Кулдаун по теме.** Одна и та же `type` не звучит чаще, чем раз в `cooldown_s`, даже если событие новое.
- **Отсутствие пользователя.** В `afk` всё, кроме `alert`, копится в дайджест и отдаётся одной фразой при возвращении.

### Шаг 3 — модель

Вызывается только после RAISE и пройденных бюджетов. Получает пакет:

- само событие,
- последние 5 событий из журнала (для связности),
- состояние сессии: что запущено, что на переднем плане, чем занимались,
- краткую память: релевантные факты о пользователе,
- список доступных инструментов.

В системном промпте явно разрешён исход «промолчать»: модель может вернуть `{"speak": false}`. Это дешевле, чем городить ещё один слой правил, и именно так лечится назойливость.

## Пример rules.yaml

```yaml
- id: relay-loss
  match: { type: "net.loss.high", context.session: "gaming" }
  action: ACT
  tool: relay.switch_route
  say: "Потери на маршруте, переключаю relay."

- id: relay-loss-idle
  match: { type: "net.loss.high" }
  action: RAISE
  reason: "вне игры решение неочевидно, пусть спросит"

- id: czn-launch
  match: { type: "process.started", subject.app: "ChaosZeroNightmare.exe" }
  action: ACT
  tool: overlay.attach
  say: null

- id: game-audio-full
  match: { type: "process.started", subject.app: "in:settings.games.list" }
  guard: "audio.music_playing()"
  action: ASK
  question: "Играет музыка. Переключить на наушники и приглушить?"
  on_yes:
    - { tool: audio.set_default_output, args: { device: "@settings.audio.devices.headphones", require_present: true } }
    - { tool: audio.duck_music, args: { level: "@settings.audio.music.duck_level" } }
  ttl_s: 45
  auto_promote: true

- id: game-audio-route
  match: { type: "process.started", subject.app: "in:settings.games.list" }
  guard: "not audio.music_playing()"
  action: ACT
  tool: audio.set_default_output
  args: { device: "@settings.audio.devices.headphones", require_present: true }
  say: null

- id: game-audio-restore
  match: { type: "process.stopped", subject.app: "in:settings.games.list" }
  action: ACT
  tools: [audio.restore_default_output, audio.unduck_music]
  say: null

- id: lumina-done
  match: { type: "job.done", subject.job: "lumina.*" }
  action: RAISE
  budget: ambient

- id: gpu-hot
  match: { type: "metrics.gpu.hot", payload.temp_c: ">= 85" }
  action: RAISE
  severity_override: alert

- id: metrics-noise
  match: { type: "metrics.*" }
  action: DROP
```

Порядок важен: частные правила выше общих, последним стоит глушилка для всего остального.

## Отложенные вопросы

Исход ASK превращает событие в вопрос, на который ассистент ждёт ответа. Ключевое требование: инструмент выбирается **до** того, как вопрос задан. Иначе после «да» будет второй заход в модель и лишняя секунда молчания.

### Пакет от модели

```json
{
  "speak": true,
  "text": "Играет музыка. Переключить на наушники и приглушить?",
  "expect": ["yes", "no"],
  "on_yes": [
    { "tool": "audio.set_default_output", "args": { "device": "Наушники" } },
    { "tool": "audio.duck_music", "args": { "level": 20 } }
  ],
  "on_no": null,
  "ttl_s": 45,
  "rule_id": "game-audio-full"
}
```

`on_yes` — всегда список, даже из одного элемента. Действия выполняются по порядку, при ошибке любого остальные откатываются. Это важно для составных вопросов: два отдельных вопроса подряд («переключить?» и следом «приглушить?») ощущаются как допрос, поэтому связанные действия объединяются в один вопрос с одним «да».

Для правил с готовым `on_yes` (как `game-audio-full`) модель не нужна вообще — пакет собирается из самого правила.

### Жизненный цикл

1. Создаётся `pending_question` с TTL 30–60 с.
2. STT переходит в режим короткого ответа: **wake word не требуется**. Распознаются «да», «давай», «ага», «нет», «не надо», «потом». Всё остальное считается новой темой — вопрос снимается как проигнорированный, реплика уходит в обычный конвейер.
3. Согласие — выполняется `on_yes`. Подтверждение либо короткое, либо молчаливое: пользователь и так услышит, что музыка стала тише.
4. Отказ — `deny++`, ничего не делается.
5. Таймаут — `ignore++`, тихо, без напоминания.
6. Событие с `severity: alert` снимает pending и проходит вперёд.
7. Одновременно живёт **один** вопрос. Новый вытесняет старый, старый засчитывается как проигнорированный.

### Отмена вместо вопроса

Для обратимых действий вопрос не задаётся, но 60 секунд держится `last_action` со ссылкой на обратную операцию. Голосовое «отмени» откатывает последнее действие. Это лучше вопроса: в девяти случаях из десяти пользователь согласился бы, а десятый чинится одним словом.

### Правила учатся сами

Таблица `rule_stats(rule_id, subject, confirm, deny, ignore, state, updated_at)`.

| Условие | Что происходит |
|---|---|
| 3 согласия подряд, `auto_promote: true` | Правило переводится в ACT — больше не спрашивает, просто делает |
| 3 отказа подряд | Правило усыпляется на 30 дней |
| 3 игнора подряд | Правило перестаёт озвучиваться, только пишет в журнал |

Счётчики ведутся с разбивкой по `subject`, чтобы «да» для Valorant не превращалось в автоматику для всех игр разом. Сброс счётчика — при любом противоположном ответе.

Это заменяет экран настроек: поведение подстраивается из употребления, а не из галочек.

## Переключение вывода звука

Отдельно, потому что тут есть подвох. Публичного API для смены устройства по умолчанию в Windows нет. Рабочие варианты:

| Способ | Комментарий |
|---|---|
| `SoundVolumeView.exe /SetDefault "Наушники" 1` (NirSoft) | Проще всего, умеет ещё и громкость отдельных приложений. Рекомендую |
| PowerShell, модуль AudioDeviceCmdlets | Без внешних бинарников, но медленнее на старте |
| COM-интерфейс IPolicyConfig через comtypes | Недокументированный, зато без зависимостей |

Перед переключением проверять, что устройство реально присутствует (`require_present: true`), иначе вывод уедет в отсутствующие наушники и звука не будет вообще. Прежнее устройство запоминается, чтобы `audio.restore_default_output` вернул его при выходе из игры.

### Как понять, что играет музыка

Два механизма, и нужны оба.

**SMTC — что именно играет.** `Windows.Media.Control.GlobalSystemMediaTransportControlsSessionManager` через пакет `winsdk` отдаёт список медиа-сессий с идентификатором приложения, статусом воспроизведения и метаданными трека. Это правильный источник ответа на вопрос «играет ли музыка»: работает и с десктопным приложением Яндекс Музыки, и с браузером, и заодно даёт название трека, если захочется его озвучивать.

**pycaw — чем управлять.** Перебор активных аудиосессий даёт объекты громкости для конкретных процессов. Отсюда же `GetPeakValue()` как подстраховка, если приложение не публикует себя в SMTC.

Подвох с браузером: если музыка играет во вкладке, аудиосессия принадлежит браузеру целиком, и приглушение затронет всё, что в нём звучит. Поэтому в настройках у метода два значения: `duck` для десктопного приложения и `pause` для браузера — во втором случае вместо приглушения отправляется media-key пауза через SMTC.

### Настройки

Всё, что зависит от конкретной машины, выносится в конфиг и заполняется из UI, а не руками:

```yaml
audio:
  devices:
    speakers:   "Динамики (Realtek High Definition Audio)"
    headphones: "Наушники (WH-1000XM4)"
    restore_on_game_exit: true
  music:
    apps: ["Яндекс Музыка.exe"]   # выбирается из списка активных сессий
    duck_level: 20                # проценты от текущей громкости
    method: duck                  # duck | pause

games:
  list: ["VALORANT-Win64-Shipping.exe", "ChaosZeroNightmare.exe"]
  detect_fullscreen: true         # плюс автодетект по эксклюзивному полноэкранному режиму
```

Для экрана настроек нужны два вспомогательных вызова: `audio.list_devices()` и `audio.list_sessions()`. Тогда устройства и музыкальные приложения выбираются из выпадающего списка, а не вводятся строкой — имена процессов у Яндекс Музыки различаются между версиями и написаны кириллицей, руками их вбивать бессмысленно.

`games.list` со временем должен наполняться сам: `detect_fullscreen` ловит переход в эксклюзивный полноэкранный режим, и после третьего запуска приложение можно молча добавить в список, спросив один раз.

## Куда попадает результат

Чат на главном экране — это диалог, а не системный лог. В него идёт только то, где пользователь был участником. Раскладка ложится на исходы фильтра:

| Исход | Чат | Голос | Звук | Тост |
|---|---|---|---|---|
| `RAISE` от голосовой команды | да | да | нет | нет |
| `ASK` | да, одним сообщением | да | да | если окно не в фокусе |
| `RAISE` фоновый (`notice`) | нет | по бюджету | если не в фокусе | нет |
| `ACT` | нет | опционально | подтверждение | нет |
| `DROP` | нет | нет | нет | нет |

`ASK` сворачивается в один пузырь вместе с исходом («Приглушил музыку»), а не в три записи подряд.

Неочевидная причина держать границу жёстко: всё, что лежит в чате, обычно уезжает и в контекст модели. Если фоновые события копятся в истории сообщений, модель начинает на них ссылаться, и через час разговор превращается в обсуждение пинга. Текущее состояние подавать отдельным компактным блоком, а не прошлыми ambient-репликами.

Возражение «тогда я не узнаю, зачем оно переключило звук» снимается инструментом `journal.recent(minutes)`: модель поднимет запись из журнала, когда её спросят. Держать событие в чате ради этого не нужно.

Возвращение из AFK — не двенадцать сообщений, а одна свёрнутая карточка «пока тебя не было: 3 события», разворачивается по клику.

### Звук и уведомления

Звуков ровно три, больше не заводить: подтверждение действия, вопрос, тревога. Всё остальное молча.

- `alert` звучит всегда;
- `notice` — только когда окно не в фокусе;
- `ambient` не звучит никогда;
- в `gaming` и при активном микрофоне в звонке — тишина, кроме `alert`.

Файлы короткие, до 300 мс, отдельный канал микшера, чтобы громкость уведомлений настраивалась независимо от Sonara. Звук и речь не накладываются: сначала сигнал, потом фраза.

Системные тосты Windows (`local_notifier` или `windows_notification`) закрывают дыру в отложенных вопросах: кнопка в тосте позволяет ответить на `ASK`, когда отвечать голосом неудобно — например в игре.

## Состояние моделей

Гемма живёт в видеопамяти постоянно (`keep_alive` без срока) и выгружается только на время работы Lumina, когда её место занимает модель генерации. Арбитр загрузки уже управляет этим — задача шины не дублировать его, а получать от него события.

Арбитр публикует два события:

| Событие | Когда | Что несёт |
|---|---|---|
| `model.evicted` | гемма выгружена под Lumina | причина, ожидаемое время возврата |
| `model.ready` | гемма вернулась | — |

Фильтр держит из них один флаг в состоянии сессии. Отдельный реестр возможностей не нужен: источник истины один — арбитр.

Правило объявляет свою потребность строкой `requires: llm`. Если мозг занят, фильтр выбирает по severity:

| Severity | Поведение при выгруженной гемме |
|---|---|
| `alert` | деградировать: фиксированная фраза из пула, синтез из кэша |
| `notice` | отложить в очередь, умереть по своему `ttl_s`, если не дождалось |
| `info` | выбросить сразу |

Важное следствие: `ACT` и `ASK` с готовым `on_yes` из правила работают всё это время как обычно — модель им не нужна. Ждать приходится только свободному разговору. Это ещё один аргумент держать реестр правил живым.

Десятиминутный таймер выгрузки модели генерации шины не касается: это внутренняя экономия видеопамяти, ни одно правило от неё не зависит. Наружу публикуется только `job.failed`, если запрос упёрся в момент загрузки.

Голосовая команда во время генерации выполняется правилами. Свободный разговор — ставится в очередь с короткой фразой «отвечу, как закончится генерация».

## Фразы и кэш озвучки

Одна и та же строка на каждое срабатывание убивает ощущение живости быстрее, чем что-либо ещё. Поэтому в правиле не строка, а ссылка на пул.

```sql
CREATE TABLE phrases (
  id          INTEGER PRIMARY KEY,
  rule_id     TEXT NOT NULL,
  slot        TEXT NOT NULL,      -- say | question | confirm
  text        TEXT NOT NULL,
  source      TEXT DEFAULT 'seed',-- seed | generated
  enabled     INTEGER DEFAULT 1,
  used_at     TEXT,
  audio_path  TEXT,               -- путь к готовому wav
  audio_voice TEXT,               -- каким голосом синтезировано
  audio_ms    INTEGER,
  UNIQUE(rule_id, slot, text)
);
```

Выбор в рантайме: случайная запись по `rule_id` и `slot` среди `enabled = 1` с непустым `audio_path`, исключая последнюю использованную. Без этого исключения рандом рано или поздно повторится дважды подряд, и весь эффект пропадёт.

### Пополнение пула

Фразы из правил переезжают в таблицу с самого начала с `source: seed`. Генерация — необязательное дополнение поверх, а не требование: не сработала, работают исходные.

Запуск по событию `model.idle`, не по расписанию — ночью машина может быть выключена, а момент простоя случается каждый день. Промпт с жёсткой схемой:

```
Придумай 8 вариантов фразы для ситуации: <описание правила>.
Тон: короткий, дружелюбный, без канцелярита. До 7 слов.
Ответ строго JSON: {"phrases": ["...", "..."]}
```

Валидатор: снять markdown-обрамление (гемма без нативного tool calling иногда заворачивает JSON в блок), один ретрай при неудаче, проверить длину, отсутствие плейсхолдеров и дублей с уже сохранёнными.

### Синтез сразу после записи

Новая фраза пишется с `enabled: 0` и уходит в очередь синтеза. Включается только когда `audio_path` заполнен. Так в рантайме не бывает состояния «фраза есть, озвучки нет» — а значит, не бывает и внезапной задержки.

Правила кэша:

- **Голос — часть ключа.** При смене голоса или его настроек старые записи помечаются на пересинтез, но продолжают играть прежними файлами до готовности новых. Молчать хуже, чем говорить старым голосом.
- **Параметризованные фразы не кэшируются.** «Потери восемь процентов» синтезировать заранее нельзя. Такие фразы переписываются без чисел («потери на маршруте, переключаю») — для рефлекса точное значение не нужно, оно видно в интерфейсе.
- **Потолок 20 фраз на правило**, дальше не добавлять.
- **Чистка:** отключённые записи и файлы, не игранные полгода, удаляются вместе с аудио.
- **Отказ от фразы.** Голосовое «так больше не говори» гасит последнюю произнесённую по `used_at` через `enabled = 0`. Seed-фразы не удаляются никогда — это страховка от неудачной генерации.

Побочный эффект, ради которого всё это и стоит делать: с готовым кэшем ассистент отвечает на правила мгновенно даже когда гемма выгружена под Lumina. Свободный разговор кэшем не лечится — там спасает только стриминг: первое предложение уходит в синтез, пока модель дописывает остальное.

## Расширение: Nextcloud

Две разные задачи, и путать их не надо.

**Окно просмотра логов** — основное. Смысл в том, чтобы не лазить в браузер, а оттуда в настройки сервера. Источник — файл `nextcloud.log` по SSH через Tailscale, а не API приложения Log Reader: файл читается даже когда сам Nextcloud лежит, и ничего не требует включать на сервере.

Формат — JSON построчно, поля `reqId`, `level`, `time`, `app`, `message`, `exception`. Интересны уровни 3 и 4 (error, fatal).

Что делает окно полезнее браузера:

- фильтр по уровню одной кнопкой, по умолчанию только error и выше;
- группировка по `reqId` — одна ошибка даёт пять-шесть записей с общим идентификатором, свернуть в строку с раскрытием;
- `exception` свёрнут, полный стектрейс по клику;
- кнопка «скопировать запись»;
- живой хвост с автопрокруткой, которая останавливается при прокрутке вверх.

Реализация: читать с конца, последние ~500 строк, дальше подгрузка по запросу. Парсить построчно с `try/except` на каждой — в лог иногда попадают не-JSON строки от PHP fatal error, и одна такая не должна ронять окно.

**Алерты** — второе, поверх того же читателя хвоста. Особенность класса: действий по ним не предпринять, поэтому единственное осмысленное действие — показать.

```yaml
- id: nc-error
  match: { type: "nc.log.error" }
  action: ASK
  question: "Nextcloud пишет ошибку в {{ app }}. Показать лог?"
  on_yes: [{ tool: window.open, args: { view: "nextcloud-log", focus_req: "{{ reqId }}" } }]
  ttl_s: 60
```

Против спама, а Nextcloud умеет сыпать одной ошибкой сотнями:

- **Дедуп по `app` плюс первые слова сообщения**, не по `reqId` — идентификатор запроса у каждой записи свой, схлопывания по нему не будет. Окно подавления 15 минут.
- **Счётчик вместо повторов.** Повторы растят `repeat_count`; при открытии окна видно «47 раз за час», что информативнее сорока семи реплик.
- **Первое за сессию озвучить, дальше молча в бейдж** с числом непрочитанных на иконке расширения.
- **Severity — `notice`, не `alert`.** Ошибки сервера почти никогда не срочные, во время игры ассистент должен промолчать. Настоящий `alert` заслуживает разве что кончающееся место на диске: оно чинится до того, как всё встанет.

## Очередь и приоритеты

Три полосы, обслуживаются строго по приоритету:

1. `interactive` — голосовая команда. Всегда первая, прерывает озвучку любой полосы ниже.
2. `alert` — то, что нельзя не сказать.
3. `ambient` — фоновые наблюдения. Дропается при переполнении и по `ttl`.

Barge-in: событие `voice.wake` во время работы TTS обрывает синтез на текущем чанке и очищает очередь `ambient`.

## Журнал

Все события пишутся в SQLite (`events` с индексом по `ts` и `type`), включая отброшенные, с отметкой на каком шаге умерли. Даёт две вещи: отладку правил без переигрывания сценария и ответ на вопрос «что произошло, пока меня не было».

Ретенция: подробности 7 дней, дальше только `alert` и `voice.*`.

## Память

Сразу разделить два хранилища, которые легко перепутать:

- **Состояние сессии** — что запущено, что на переднем плане, о чём говорили последние двадцать минут. Живёт в оперативке, умирает с сессией.
- **Память** — кто ты, чем занимаешься, какие у тебя проекты и привычки. Живёт в SQLite годами.

Хранятся факты, а не диалоги. Транскрипт бесполезен: он длинный, и в нём всё равно надо искать. Хранится извлечённое утверждение.

### Схема

```sql
CREATE TABLE subjects (
  name       TEXT PRIMARY KEY,   -- profile, nexus-relay, lumina, hardware
  kind       TEXT,               -- profile | project | preference | device | person
  summary    TEXT NOT NULL,      -- одна строка: что тут и когда это читать
  updated_at TEXT
);

CREATE TABLE facts (
  id         INTEGER PRIMARY KEY,
  subject    TEXT REFERENCES subjects(name),
  text       TEXT NOT NULL,
  confidence REAL DEFAULT 1.0,
  ts         TEXT,
  ttl_days   INTEGER,            -- NULL = бессрочно
  last_used  TEXT,
  use_count  INTEGER DEFAULT 0
);

CREATE INDEX idx_facts_subject ON facts(subject);
```

### Оглавление вместо поиска

В системный промпт всегда кладётся список субъектов с их `summary` — это 200–300 токенов. Модель сама решает, что открыть, обычным вызовом инструмента:

- `memory.read(subject)` — вернуть факты по субъекту;
- `memory.write(subject, text)` — добавить факт;
- `memory.forget(subject, text)` — удалить.

Векторный поиск понадобится сотен через пять фактов, не раньше. Когда дойдёт — для русского брать bge-m3 или multilingual-e5, но начинать с него не надо: оглавление проще, дешевле и отлаживается глазами.

### Извлечение — фоновым проходом

В реальном времени факты не извлекаются, это убьёт задержку. После завершения сессии отдельный вызов модели получает транскрипт, список уже известных фактов по затронутым субъектам и такую инструкцию:

```
Выдели из разговора устойчивые факты о пользователе и его проектах.
Правила:
- максимум 3 факта;
- только то, что будет верно и через месяц;
- сиюминутное состояние (что запущено, о чём спросили) не сохранять;
- если факт противоречит известному — вернуть replace с id старого;
- если факт уже известен — не возвращать вовсе;
- пароли, токены, ключи и содержимое экрана не сохранять никогда.

Ответ строго JSON:
{"facts": [{"op": "add|replace", "subject": "...", "text": "...", "replaces": null}]}
```

Ограничение в три факта важнее, чем кажется: без него модель за месяц набьёт базу мусором вроде «пользователь спрашивал про иконку», и оглавление перестанет помещаться в промпт.

### Гигиена

- Перед вставкой сравнивать с фактами того же субъекта: заменять, а не копить дубли. Иначе через месяц там будет три разных ответа про одну видеокарту.
- `last_used` обновлять при каждом чтении. Факты, не читанные полгода и с истёкшим `ttl_days`, уносить в архивную таблицу.
- `summary` субъекта переписывать при заметном изменении состава фактов — это то, по чему модель принимает решение читать или нет.

## Реализация

Один процесс сайдкара, `asyncio`:

- источники — независимые продюсеры, каждый в своей корутине, пишут в `asyncio.Queue`;
- фильтр — единственный консьюмер, один поток исполнения, чтобы порядок и бюджеты были детерминированы;
- вызовы инструментов и модели — в отдельном пуле, фильтр их не ждёт;
- падение источника не роняет шину: каждый продюсер обёрнут в супервизор с рестартом.

Сначала интерфейс `EventSource` с одним методом-генератором — тогда новый источник добавляется файлом на 30 строк.

## Что делать первым

Минимальный срез, который уже даёт живого ассистента в одном сценарии:

1. Шина, формат события, журнал в SQLite.
2. Три источника: `system.process`, `net.relay`, `job`.
3. Правила из примера выше, включая переключение звука и вопрос про музыку.
4. Таблица `phrases` с seed-фразами и кэшем озвучки. Без генерации — она поверх.
5. Бюджет: token bucket и тишина в полноэкранном режиме.
6. Отложенные вопросы с TTL и `rule_stats` — без них ASK превращается в назойливость.
7. Разделение поверхностей: что в чат, что в тост, что только в журнал.

Вторым этапом: события арбитра и деградация при выгруженной гемме, генерация фраз, память. Расширение Nextcloud идёт отдельно и от шины почти не зависит — сначала окно, алерты позже.

Когда игровой сценарий отработает от запуска CZN до фразы про relay, подключать модель и остальные источники.

## Сквозной пример

```
14:02:11  net.relay → net.loss.high (8.4%, route vps-fra)
14:02:11  Шаг 0: дедуп пройден, ttl ок
14:02:11  Шаг 1: правило relay-loss → ACT
14:02:11  tool relay.switch_route(vps-fra → vps-hel) → ok за 340 мс
14:02:12  say: "Потери на маршруте, переключаю relay."
14:02:12  журнал: acted, модель не будилась
14:03:40  net.relay → net.loss.recovered → правило DROP, только журнал
```

Модель в этом сценарии не участвовала ни разу. Так и должно быть: она нужна для разговора, а не для рефлексов.
